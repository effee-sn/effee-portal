# Effee Portal — RBAC Boilerplate

Odoo-inspired admin boilerplate with role-based access control. Separate frontend and backend communicating over REST.

| | Stack |
|---|---|
| **Frontend** | Next.js 16 (App Router), React 19, Tailwind CSS 4 |
| **Backend** | Node.js, Express 5, Prisma 5 |
| **Database** | MySQL 8 / MariaDB 10.4+ |
| **Language** | JavaScript with JSDoc type annotations (no TypeScript, no build step) |

---

## Quick start

**Prerequisites:** Node.js 18+, a running MySQL or MariaDB server.

```bash
# 1. Create the database
mysql -u root -e "CREATE DATABASE effeeportal CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;"

# 2. Backend
cd Backend
npm install
cp .env.example .env          # then edit — see Configuration below
npm run setup                 # prisma generate + db push + seed
npm run dev                   # → http://localhost:4000

# 3. Frontend (in a second terminal)
cd Frontend
npm install
echo "NEXT_PUBLIC_API_URL=http://localhost:4000/api" > .env.local
echo "NEXT_PUBLIC_UPLOADS_URL=http://localhost:4000" >> .env.local
npm run dev                   # → http://localhost:3000
```

The seeder prints a randomly generated Super Admin password **once**. Record it — it is stored nowhere else.

### Known install issue

npm 11 blocks package install scripts by default, which means **Prisma Client is not generated by `npm install`**. `npm run setup` runs `prisma generate` explicitly, so the flow above works. If you install manually, run `npx prisma generate` yourself or you will get `@prisma/client did not initialize yet`.

## Configuration

All backend environment variables are declared and validated in [`src/config/env.js`](Backend/src/config/env.js). Nothing else in the codebase reads `process.env` directly.

Invalid configuration **aborts startup in production** and logs a warning in development.

| Variable | Required | Default | Notes |
|---|---|---|---|
| `DATABASE_URL` | **yes** | — | Prisma connection string |
| `JWT_SECRET` | **yes** | — | Minimum 32 characters |
| `NODE_ENV` | no | `development` | `production` makes config errors fatal |
| `PORT` | no | `4000` | |
| `JWT_EXPIRES_IN` | no | `7d` | |
| `BCRYPT_ROUNDS` | no | `12` | Cost is stored per-hash, so raising it later is safe |
| `ALLOWED_ORIGIN` | no | `http://localhost:3000` | Comma-separated. First entry is the base for reset links |
| `TRUST_PROXY_HOPS` | no | `0` | Number of reverse proxies. **Set correctly or rate limiting is bypassable** |
| `ENCRYPTION_KEY` | no | derived from `JWT_SECRET` | 32 bytes, base64 or hex. See warning below |
| `LOG_LEVEL` | no | `debug` / `info` | |
| `SEED_ADMIN_EMAIL` | no | `admin@admin.com` | |
| `SEED_ADMIN_PASSWORD` | no | generated | **Required** when `NODE_ENV=production` |

Generate secrets:

```bash
node -e "console.log(require('crypto').randomBytes(48).toString('base64url'))"   # JWT_SECRET
node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"      # ENCRYPTION_KEY
```

> **`ENCRYPTION_KEY` and `JWT_SECRET`**
> When `ENCRYPTION_KEY` is unset, the field-encryption key is derived from `JWT_SECRET` via HKDF. That works out of the box, but it means **rotating `JWT_SECRET` makes existing encrypted values undecryptable** — currently the stored SMTP password. Set `ENCRYPTION_KEY` explicitly in any environment where you expect to rotate the JWT secret.

## Architecture

Every backend module is five files with strictly one-way dependencies:

```
routes → validation → controller → service → repository → Prisma
```

| Layer | Responsibility | Must never |
|---|---|---|
| `*.routes.js` | Wiring: authenticate → authorize → validate → handler | Contain logic |
| `*.validation.js` | Zod schemas — the input contract | Touch the database |
| `*.controller.js` | HTTP only: read request, call service, send response | Import Prisma or bcrypt |
| `*.service.js` | Business rules, hashing, guards, audit | Reference `req`/`res` or HTTP status codes |
| `*.repository.js` | Data access — the only file importing Prisma | Throw `AppError`s |

These boundaries are **enforced by test**, not convention — `tests/integration` greps the source and fails if a controller imports Prisma or a service references `res`.

### Adding a module

1. Create `src/modules/<name>/` with the five files.
2. Register one line in [`src/routes/index.js`](Backend/src/routes/index.js).
3. Add the module and its permissions to `PERMISSIONS` in [`prisma/seed.js`](Backend/prisma/seed.js), then `npm run seed`.

### The core layer

Shared infrastructure lives in [`src/core/`](Backend/src/core) and is imported through its barrel:

```js
const { asyncHandler, validate, ApiResponse, NotFoundError, parseListQuery } = require('../../core');
```

- **`errors/`** — `AppError` and seven subclasses. Operational errors carry client-safe messages; everything else is replaced with a generic 500 so Prisma internals never leak.
- **`http/`** — `asyncHandler`, `ApiResponse`, `parseListQuery` (pagination, sorting, filtering, search), `requestContext`.
- **`validation/`** — Zod middleware plus reusable schemas.
- **`logging/`** — pino with credential redaction and `X-Request-Id` correlation.
- **`middleware/`** — the terminal error handler.

## API

Base URL: `/api/v1` (canonical) or `/api` (legacy alias — the frontend uses this).

### Response shapes

Existing endpoints return **unwrapped** payloads, because the frontend reads them directly:

```jsonc
// GET /api/users
{ "users": [...], "total": 57, "page": 1, "limit": 10, "pages": 6 }
```

New endpoints use the envelope:

```jsonc
// GET /api/audit-logs
{ "success": true, "data": [...], "meta": { "pagination": { ... } } }
```

Errors are uniform, and always include `message` for backwards compatibility:

```jsonc
{
  "success": false,
  "message": "Validation failed",
  "code": "VALIDATION_FAILED",
  "details": [{ "field": "email", "message": "Must be a valid email address" }],
  "request_id": "0f8c…"
}
```

### List parameters

Supported by collection endpoints: `?page=`, `?limit=` (max 100), `?search=`, `?sort=`, `?order=asc|desc`, plus per-module filters.

Sortable and filterable fields are **whitelisted per module**. This is a security control: `orderBy` keys are structural SQL, not bound parameters, so an unchecked field name would let a caller sort by `password` and binary-search the hash.

### Endpoints

| Method | Path | Access |
|---|---|---|
| `POST` | `/auth/login` | public, rate limited |
| `POST` | `/auth/forgot-password` | public, rate limited (per IP **and** per email) |
| `POST` | `/auth/reset-password` | public, rate limited |
| `GET` | `/auth/me`, `/auth/profile` | authenticated |
| `PUT` | `/auth/profile`, `/auth/change-password` | authenticated |
| `GET` | `/dashboard` | authenticated (content varies by permission) |
| `GET` | `/lookup/{roles,users,permissions,modules}` | authenticated |
| `GET/POST/PUT/DELETE` | `/users`, `/users/:id` | `USER_VIEW` / `USER_CREATE` / `USER_EDIT` / `USER_DELETE` |
| `GET/POST/DELETE` | `/roles`, `/roles/:id` | `ROLE_VIEW` / `ROLE_CREATE` / `ROLE_DELETE` |
| `PUT` | `/roles/:id/permissions` | `ROLE_EDIT` |
| `PATCH` | `/roles/:id` | `ROLE_EDIT` (descriptive fields only) |
| `GET` | `/settings` | authenticated — **response filtered by role** |
| `PUT/POST` | `/settings/*` | system administrator only |
| `GET` | `/audit-logs` | system administrator only, read-only |
| `GET` | `/health` | public liveness probe |

## Authorization

Two mechanisms, chosen by what is being protected:

```js
router.get('/', authorize('USER_VIEW'), handler);          // permission-based
router.put('/email', requireSystemRole, handler);          // platform configuration
```

`authorize()` reads the permission set that `authenticate` already resolved onto `req.user`, so it costs no extra query. Roles flagged `is_system` bypass all permission checks.

Use `requireSystemRole` only for things that cannot be expressed as a module permission — SMTP credentials, rate-limit thresholds, the audit trail. Anything else belongs in the Module/Permission model so it stays manageable from the Roles screen.

## Security

| Control | Implementation |
|---|---|
| Password hashing | bcrypt, cost 12, with a timing-equalised failure path to prevent account enumeration |
| Password policy | 8–72 bytes, two character classes, common-password blocklist — [`lib/passwordPolicy.js`](Backend/src/lib/passwordPolicy.js) |
| JWT | HS256 **pinned** on verify, so a forged token cannot request a weaker algorithm |
| Secrets at rest | SMTP password encrypted with AES-256-GCM — [`lib/crypto.js`](Backend/src/lib/crypto.js) |
| Rate limiting | Login (admin-configurable), forgot-password (per IP + per email), reset-password |
| Input validation | Zod at the boundary; unknown keys stripped, blocking mass assignment |
| CORS | Explicit origin allowlist |
| Uploads | MIME→extension whitelist, random filenames, SVG rejected (stored-XSS vector) |
| Audit trail | Append-only, secrets redacted, no write routes exposed |
| Error disclosure | 5xx messages replaced with a generic string; stack traces development-only |

### Known limitations

These are real and deliberate; fix them before relying on this in production at scale.

1. **Rate limiting is in-process.** The counter lives in a `Map`, so it resets on restart and is not shared between instances. Move to Redis before running more than one backend node.
2. **`TRUST_PROXY_HOPS` must match your topology.** Set too high, a client can spoof `X-Forwarded-For` and evade rate limiting entirely. Set too low behind a proxy, every client shares one bucket.
3. **No token revocation.** Logout is client-side; a stolen token stays valid until it expires. Shorten `JWT_EXPIRES_IN` or add a refresh-token flow with a denylist.
4. **Tokens live in `localStorage`** on the frontend, so they are XSS-exfiltratable. httpOnly cookies plus CSRF tokens is the stronger design.
5. **Search uses `LIKE '%term%'`**, which cannot use an index. Fine at current volumes; switch to FULLTEXT past ~100k rows. Isolated in `buildSearchClause` so it changes in one place.

## Database

Conventions applied across the schema:

- **Soft deletes** — `deleted_at` rather than `DELETE`. Repositories filter it automatically, so the rest of the codebase is unaware. `email` and `phone` remain globally unique *including* soft-deleted rows, so a departed user's address cannot be reused and make audit history ambiguous.
- **Audit fields** — `created_by` / `updated_by` as plain `Int`, deliberately not foreign keys: a relation would block deleting any user who had ever touched a record.
- **Audit log** — append-only `AuditLog` table recording actor, IP, user agent, and `request_id`, which correlates with the application log.
- **Indexes** — every column used in a `WHERE`, `ORDER BY`, or `JOIN`. Do not add `@@index` on a foreign key; MySQL creates one automatically and Prisma will fail trying to drop it.

```bash
npm run db:push       # apply schema changes (development)
npm run db:migrate    # create a migration (production workflow)
npm run db:studio     # browse data
npm run seed          # idempotent — safe to re-run to apply new permissions
```

## Testing

```bash
npm test              # unit — no database required
npm run test:integration
npm run test:all
npm run test:watch
```

Integration tests boot the real app on an ephemeral port and hit it over HTTP — nothing is mocked. They need a seeded database and admin credentials:

```bash
# PowerShell
$env:TEST_ADMIN_EMAIL="admin@admin.com"; $env:TEST_ADMIN_PASSWORD="…"; npm run test:integration

# bash
TEST_ADMIN_EMAIL=admin@admin.com TEST_ADMIN_PASSWORD=… npm run test:integration
```

Without those variables the integration suites **skip with a warning** rather than fail, so `npm test` stays green on a machine with no database.

Logs are silenced automatically under the test runner. Set `LOG_LEVEL=debug` to see them while debugging a failure.
