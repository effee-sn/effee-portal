Effee Portal — Installation & Deployment Guide
==============================================

Effee Portal is the company's internal business portal: Service (tickets and
department tasks), Sales (enquiries to orders), Projects, Master Data
(customers, contacts, currencies), Reports (MIS) and Administration, with
role-based access control. The frontend (Next.js) and backend (Express +
Prisma) run as two separate apps that talk over REST.

There is NO web install wizard. Setup is: create an empty database, fill in the
environment files, run the setup script, then start the two apps.

The portal is an in-house application and is meant to run on the internal
network (office LAN / company VPN), not on the public internet.


1. Prerequisites
----------------
  Node.js      v20.9 or higher (v22 LTS recommended)   https://nodejs.org
               (Next.js 16 does not run on Node 18.)
  MySQL 8+  or MariaDB 10.6+                           https://mysql.com / https://mariadb.org
  Git          any                                     https://git-scm.com

  Production server (around 10–30 users):
    4 vCPU, 8 GB RAM, 128 GB SSD, Ubuntu Server 24.04 LTS (22.04 also fine),
    PM2 (process manager), nginx (reverse proxy), an HTTPS certificate for the
    portal's domain.


2. Get the project
------------------
  git clone <repo-url> effeeportal
  cd effeeportal

  Folder layout:
    Backend/    the API      (Express + Prisma)
    Frontend/   the web app  (Next.js)


3. Create the database
----------------------
Create an EMPTY database — the setup step creates all the tables.

  mysql -u root -e "CREATE DATABASE effeeportal CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;"


4. Configure the backend
------------------------
  cd Backend
  cp .env.example .env

Then edit .env. Every setting is explained in .env.example; the main ones:

  Core (required)
    DATABASE_URL       mysql://user:password@localhost:3306/effeeportal
    JWT_SECRET         a random string, at least 32 characters
                       node -e "console.log(require('crypto').randomBytes(48).toString('base64url'))"
    NODE_ENV           development (local) or production (server)
    PORT               4000 by default
    ALLOWED_ORIGIN     the portal's address as users open it, e.g.
                       https://portal.effee-induction.com  (http://localhost:3000 locally)
                       Also used for the links in emails and notifications.
    TRUST_PROXY_HOPS   0 = direct, 1 = behind nginx

  First Super Admin (used by the seeder)
    SEED_ADMIN_EMAIL       the admin login email
    SEED_ADMIN_PASSWORD    leave blank in development (a random password is
                           printed once); REQUIRED when NODE_ENV=production.
                           Remove it from .env after the first setup.
    SEED_ADMIN_PHONE       optional

  Email (section 9)
    SMTP_HOST / SMTP_PORT / SMTP_USER / SMTP_PASS / SMTP_FROM_NAME / SMTP_FROM_EMAIL
    EMAIL_NOTIFICATIONS    true = email every in-app notification as well

  Browser push (section 8)
    VAPID_PUBLIC_KEY / VAPID_PRIVATE_KEY / VAPID_SUBJECT

  Microsoft sign-in (section 10)
    MS_SSO_TENANT_ID / MS_SSO_CLIENT_ID / MS_SSO_CLIENT_SECRET /
    MS_SSO_REDIRECT_URI / MS_SSO_ALLOWED_GROUP_ID

  Reminders & timezone (section 11)
    APP_TIMEZONE                     Asia/Kolkata
    FOLLOWUP_REMINDER_LEAD_MINUTES   15
    FOLLOWUP_REMINDER_DAY_TIME       09:00

  Secrets (passwords, the client secret, JWT_SECRET) live ONLY in .env, never
  in the database. .env is excluded from Git — never commit it.


5. Install and set up the backend
---------------------------------
  cd Backend
  npm install
  npm run setup        # prisma generate + prisma migrate deploy + seed

  `npm run setup` applies the database MIGRATIONS (not `prisma db push`). The
  migrations also insert built-in data the portal needs — the INR base
  currency, the sales stage probabilities and the starter applications — so
  always set a database up through migrations.

  IMPORTANT: npm may block package install scripts, so `npm install` on its own
  does NOT generate the Prisma client. `npm run setup` runs `prisma generate`
  explicitly. If you ever see "@prisma/client did not initialize yet", run
  `npx prisma generate`.

  The seeder creates the built-in roles, modules, permissions, departments,
  company settings and the Super Admin. When SEED_ADMIN_PASSWORD is not set it
  prints a random Super Admin password ONCE — copy it now.

  Start the backend:
    npm run dev          # development, auto-reload  → http://localhost:4000
    # or
    npm start            # plain start


6. Configure and start the frontend
------------------------------------
  cd ../Frontend
  npm install
  cp .env.local.example .env.local

  .env.local:
    NEXT_PUBLIC_API_URL=http://localhost:4000/api
    NEXT_PUBLIC_UPLOADS_URL=http://localhost:4000
  On the server use the portal's HTTPS address instead, e.g.
    NEXT_PUBLIC_API_URL=https://portal.effee-induction.com/api
    NEXT_PUBLIC_UPLOADS_URL=https://portal.effee-induction.com
  NEXT_PUBLIC_* values are built into the frontend — after changing them you
  must run `npm run build` again.

  Start the frontend:
    npm run dev          # development  → http://localhost:3000
    # or, for production:
    npm run build
    npm start


7. First login and initial setup
--------------------------------
Open the portal and log in with SEED_ADMIN_EMAIL and its password. Then:

  Administrator → Roles        give each role its permissions (Service, Sales,
                               Projects, Customers, Currencies, Reports,
                               Sales configuration …). Admin roles have all.
  Administrator → Users        add the users (email = their Microsoft 365
                               address if Microsoft sign-in will be used).
  Administrator → Departments  departments for service work.
  Administrator → Flow Builder Services flow, and the Sales tab: select the
                               internal sales person.
  Administrator → Settings     company name and logo; Security (login limits,
                               Microsoft sign-in).
  Master Data → Currencies     INR is built in; add USD, EUR … with rates.
  Sales → Configuration        stage probabilities and the applications list.


8. Notifications & browser push
-------------------------------
In-app notifications (the bell in the top bar) work out of the box.

Browser push (desktop/phone pop-ups, even when the portal is closed) needs:

  a) VAPID keys in the backend .env. Generate a pair once:
       node -e "console.log(require('web-push').generateVAPIDKeys())"
     then set them and restart the backend:
       VAPID_PUBLIC_KEY=<publicKey>
       VAPID_PRIVATE_KEY=<privateKey>
       VAPID_SUBJECT=mailto:admin@effee-induction.com
     Keep the same keys for good — changing them breaks every existing
     subscription.

  b) HTTPS with a certificate the users' browsers trust (localhost excepted).
     Over plain HTTP the "Enable desktop notifications" option does not appear.

  c) Each user enables it once from the bell. Permission is per website: if
     the portal's domain changes, users enable it again on the new domain.

If the VAPID keys are absent, push is disabled; in-app notifications and email
are unaffected.


9. Email
--------
SMTP settings live only in the backend .env. Two ways to send through
Microsoft 365:

  Authenticated SMTP (recommended — works from any network):
    SMTP_HOST=smtp.office365.com
    SMTP_PORT=587
    SMTP_USER=noreply@effee-induction.com     (a licensed mailbox with SMTP AUTH enabled)
    SMTP_PASS=<that mailbox's password>
    SMTP_FROM_EMAIL=noreply@effee-induction.com

  Direct Send (no login):
    SMTP_HOST=<tenant>.mail.protection.outlook.com
    SMTP_PORT=25
    SMTP_USER= / SMTP_PASS=   (empty)
    Needs outgoing port 25 to be open and the sending IP to be allowed by the
    domain's SPF record. Many cloud and home networks block port 25 or are on
    spam blocklists — use port 587 in that case.

  EMAIL_NOTIFICATIONS=true emails every in-app notification too. Password-reset
  emails are always sent. Check the setup with Administrator → Settings →
  Company → Email → Send test email.


10. Microsoft sign-in (SSO) — optional
--------------------------------------
Lets users sign in with their Microsoft 365 account. Roles and permissions stay
in the portal. Off until configured and switched on.

  a) Your Microsoft 365 administrator registers the portal in Microsoft Entra
     ID (single tenant), with the redirect URI (platform: Web)
       https://<portal-domain>/api/v1/auth/sso/microsoft/callback
     and gives you the Tenant ID, Client ID and a Client secret.
     Recommended: Enterprise application → Properties → "Assignment required"
     = Yes, and assign the group of people allowed to use the portal.
  b) Backend .env:
       MS_SSO_TENANT_ID=…
       MS_SSO_CLIENT_ID=…
       MS_SSO_CLIENT_SECRET=…
       MS_SSO_REDIRECT_URI=https://<portal-domain>/api/v1/auth/sso/microsoft/callback
       MS_SSO_ALLOWED_GROUP_ID=…     (optional; also add the "groups" claim in Entra)
     The redirect URI must be IDENTICAL in Entra and in .env.
  c) Restart the backend, then Administrator → Settings → Security →
     Microsoft sign-in: enable it. Optionally switch off password sign-in for
     users (the Super Admin can always sign in with a password).
  d) Each person needs a portal user with the same email as their Microsoft
     account (unless "create users automatically" is switched on).

  The server needs outgoing HTTPS to login.microsoftonline.com. Full steps
  are on the Microsoft sign-in card in Settings.


11. Reminders & timezone
------------------------
A background check runs every minute inside the backend:
  - a follow-up or review WITH a time is reminded FOLLOWUP_REMINDER_LEAD_MINUTES
    before it (15 by default) — a 5:30 meeting is reminded at 5:15;
  - a follow-up with a DATE only is reminded at FOLLOWUP_REMINDER_DAY_TIME
    (09:00) that day;
  - enquiries stuck in a stage past its time limit are reminded once per stage.
Times follow APP_TIMEZONE (Asia/Kolkata), whatever the server's own timezone.


12. Production deployment
-------------------------
On the server (Node, MySQL/MariaDB, PM2 and nginx with HTTPS assumed):

  First install: sections 3–6 with NODE_ENV=production, then start with PM2:
    cd Backend   && pm2 start src/server.js --name effee-api
    cd Frontend  && pm2 start "npm start" --name effee-web
    pm2 save

  Every update:
    git pull

    cd Backend
    npm install                 # only needed when a release adds a dependency
    npx prisma migrate deploy   # apply new database changes
    npx prisma generate
    npm run seed                # only when a release adds permissions (see notes)
    pm2 restart effee-api

    cd ../Frontend
    npm install                 # only needed when a release adds a dependency
    npm run build
    pm2 restart effee-web

  `npm run deploy` (in Backend) does generate + migrate deploy + seed in one go.

  Notes:
   - The seeder adds new modules and permissions, and re-asserts the BUILT-IN
     roles' permissions (super-admin / admin / manager / staff). If you
     customised a built-in role in the UI and don't want it reset, skip the
     seed. Custom roles created in the UI are never touched.
   - Always restart BOTH effee-api and effee-web after an update, then
     hard-refresh the browser (Ctrl + Shift + R).
   - Never run `next build` while `next dev` is running on the same folder —
     it corrupts the dev cache (fix: stop dev, delete Frontend/.next, start again).
   - nginx: serve the frontend (port 3000) at / and proxy /api and /uploads to
     the backend (port 4000). Set TRUST_PROXY_HOPS=1 in the backend .env.
   - Back up regularly — see section 13.

  Changing the portal's domain:
    1. Backend .env: ALLOWED_ORIGIN (and MS_SSO_REDIRECT_URI — change it in
       Entra too). Restart effee-api.
    2. Frontend .env.local: NEXT_PUBLIC_API_URL and NEXT_PUBLIC_UPLOADS_URL,
       then `npm run build` and restart effee-web.
    3. HTTPS certificate for the new domain.
    4. Browser push: keep the same VAPID keys; clear old subscriptions once
       (SQL: DELETE FROM PushSubscription;) and users enable push again.
       Everyone signs in again on the new domain.


13. Backups
-----------
  Easiest: in the portal, Administrator -> Backup -> "Create backup" (Super
  Admin). It makes one backup-YYYYMMDD-HHMMSS.tar.gz in Backend/backups/ with
  the database AND all uploaded files (Backend/storage/ + Backend/uploads/);
  .env is never included. "Download" it and keep the copy off the server.
  Restore from the same page puts back the database and the files. Needs
  mysqldump / mysql (MYSQL_BIN_DIR if not on PATH) and tar on the server.

  By hand, from the command line —
  Database (use the DB user and name from DATABASE_URL):
    mysqldump --no-tablespaces --single-transaction -u <db_user> -p <db_name>       > ~/portal-$(date +%Y%m%d).sql
  --no-tablespaces   needed on MySQL 8 when the DB user lacks the PROCESS
                     privilege (a normal app user does); harmless otherwise.
  --single-transaction  consistent snapshot without locking the tables.

  Check the backup isn't empty:
    ls -lh ~/portal-*.sql                      # a size in KB/MB, not 0
    grep -c "INSERT INTO" ~/portal-YYYYMMDD.sql   # > 0 (one line per table with data)

  Restore (into an existing, empty database):
    mysql -u <db_user> -p <db_name> < ~/portal-YYYYMMDD.sql

  Also back up the uploaded files: Backend/storage/ (sales documents) and
  Backend/uploads/ (logo etc.). Copy all backups off the server.


14. Resetting the database (start fresh)
----------------------------------------
  Deletes ALL data — users, enquiries, tickets, settings — and rebuilds an
  empty portal; every ID starts again from 1. Run on the server:

  1. Stop the portal
       pm2 stop all

  2. Back up first (section 13) and check the file isn't empty.

  3. Get the latest code
       cd ~/<project-folder>
       git pull

  4. Backend/.env — make sure these are set:
       NODE_ENV=production
       SEED_ADMIN_EMAIL=<the new Super Admin's email>
       SEED_ADMIN_PASSWORD=<a strong password>
       JWT_SECRET=<a NEW value: openssl rand -base64 48>   (logs out old sessions)
     plus the current settings from .env.example (APP_TIMEZONE, FOLLOWUP_*,
     MS_SSO_*, SMTP_*, VAPID_*).

  5. Wipe and rebuild the database
       cd Backend
       npm install
       npx prisma migrate reset --force --skip-seed
       npm run seed
     migrate reset drops every table and re-applies all migrations (which
     also restore the built-in INR currency, stage probabilities and
     applications) and generates the Prisma client. It ends with
     "Database reset successful". The seed creates the roles, modules,
     permissions, departments, company settings and the Super Admin; it ends
     with "Seeding complete."
     If migrate reset reports an access error, the DB user may not drop and
     re-create the database — run it as the MySQL root user.

  6. Remove the old uploaded files
       rm -rf storage/sales-docs/* uploads/*

  7. Rebuild the frontend and start
       cd ../Frontend
       npm install
       npm run build
       pm2 restart all

  8. Log in with SEED_ADMIN_EMAIL / SEED_ADMIN_PASSWORD, then REMOVE
     SEED_ADMIN_PASSWORD from Backend/.env. Users sign in again and re-enable
     browser push from the bell.

  9. Set up, in this order:
       Administrator → Departments
       Administrator → Roles        (permissions per role)
       Administrator → Users        (Microsoft 365 emails, for SSO later)
       Administrator → Flow Builder (Services flow; Sales tab: internal sales person)
       Administrator → Settings     (company name, logo)
       Master Data → Currencies     (USD, EUR … with rates; INR is built in)
       Sales → Configuration        (probabilities, applications)
       Master Data → Customers      (customers and contacts)


Ports (defaults)
----------------
  Backend API      4000
  Frontend         3000
  MySQL / MariaDB  3306


Tests (developers)
------------------
  cd Backend
  npm test                 # unit tests
  npm run test:sales       # sales rules, dashboards, reports (needs a DEV database)
  npm run test:currency    # currencies
  npm run test:sso         # Microsoft sign-in
  The integration tests create and remove their own data and refuse to run
  when NODE_ENV=production. Never point them at the live database.


Troubleshooting
---------------
mysqldump: "Access denied; you need (at least one of) the PROCESS privilege(s)"
    MySQL 8 refuses the tablespace part of the dump for a normal DB user.
    Add --no-tablespaces (section 13). The dump of the data itself is fine.

"npm warn allow-scripts … packages have install scripts not yet covered"
    npm blocked the install scripts of @prisma/client, @prisma/engines,
    prisma and bcrypt. Usually harmless (npm run setup / migrate reset run
    prisma generate). If bcrypt or Prisma then fails to load (e.g. "Cannot
    find module … bcrypt_lib.node"), allow and rebuild that package:
      npm approve-scripts bcrypt
      npm rebuild bcrypt
    (likewise for prisma / @prisma/client, followed by npx prisma generate).

"@prisma/client did not initialize yet" / Prisma client errors
    `npm install` didn't run `prisma generate` (blocked install scripts).
    Run: npx prisma generate      (or `npm run setup`).

"Cannot connect to database" / P1001
    MySQL/MariaDB not running, wrong DATABASE_URL, or the database doesn't exist.
    Create it (section 3) and check the credentials.

"Cannot find module …"  (backend won't start after a pull)
    A dependency was added but not installed on this machine.
    Run: npm install   in Backend (or Frontend), then restart.

Migration failed / P3009 "migrate found a failed migration"
    One-time recovery, then re-deploy:
      npx prisma migrate resolve --rolled-back <migration_name>
      npx prisma migrate deploy

P3005 "The database schema is not empty"
    The database was created with `prisma db push` instead of migrations.
    Set databases up with `npm run setup` / `npx prisma migrate deploy`.

500 errors right after a deploy (e.g. "unknown column")
    The database migrated but the old backend process is still running.
    Restart it: pm2 restart effee-api      (and effee-web).

New menu items or pages don't appear after an update
    The frontend wasn't rebuilt, or the browser has the old version cached.
    Run `npm run build` + `pm2 restart effee-web`, then Ctrl + Shift + R.
    New permissions (e.g. REPORT_VIEW) also need `npm run seed` and the role
    to be given the permission in Administrator → Roles.

"Enable desktop notifications" does not appear
    Browser push needs HTTPS with a trusted certificate (localhost excepted)
    AND the VAPID keys (section 8).

Test email fails: "550 5.7.1 … blocked using Spamhaus" or a timeout
    Direct Send (port 25) from a blocked IP or network. Use authenticated SMTP
    on port 587 (section 9).

Microsoft sign-in: "redirect URI mismatch" (AADSTS50011)
    MS_SSO_REDIRECT_URI in .env differs from the one registered in Entra.
    They must match character for character.

Microsoft sign-in: "There's no portal account for …"
    Add a portal user with exactly that email (Administrator → Users).

Config error aborts startup in production
    A required or weak value (e.g. JWT_SECRET under 32 characters). Fix the .env
    value; production treats config problems as fatal (a warning only in dev).
